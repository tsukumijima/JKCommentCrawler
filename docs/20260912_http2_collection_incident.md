# 2026年9月の過去ログ収集欠落と HTTP/2 の受信停止

NX-Jikkyo の過去ログ取得が受信枠の 1MiB で停止する原因は、curl-impersonate の更新で増えた HTTP/2 の設定通知と、Go の HTTP/2 サーバーがその確認応答を取り落とす不具合の組み合わせだった。  
2026年9月12日、本番と手元で停止を再現し、TLS と Caddy を使わない Go サーバーでも、未送信の確認応答を数える処理だけを変えると解消することを確認した。  
NXClient の HTTP/1.1 固定、チャンネル単位の失敗を終了コードへ反映する処理、実行ログの14日保持を本番へ適用した。  
取得したコメントと一覧ファイルは、書き込み完了後に保存先を置き換える。

9月7日から12日までの全35チャンネルを `--force` で再収集し、662,067件のコメントを102ファイルに保存した。  
日付ごとに取得結果を照合し、保存済みコメントとのマージは行っていない。

## 収集欠落までの流れ

JKCommentCrawler の依存関係は curl-cffi 0.15.0 から 0.16.3 へ更新されていた。  
0.15.0 は curl-impersonate 1.5.2 を、0.16.3 は 2.2.2 を組み込む構成であり、ベースの libcurl も 8.15.0 から 8.21.0 へ変わっている。  
curl-impersonate はブラウザーに合わせて TLS と HTTP/2 を改変した curl で、ブラウザー偽装を指定していない接続にも変更の一部が作用する。[curl-cffi のビルド指定](https://github.com/lexiforest/curl_cffi/blob/v0.16.3/scripts/build.py)、[curl-impersonate のパッチ](https://github.com/lexiforest/curl-impersonate/blob/v2.2.2/patches/curl.patch)

失敗した NX-Jikkyo の応答は約 8.66MB だったが、受信枠と同じ 1MiB で受信が止まった。  
curl は JSON の解析や保存へ進む前に、タイムアウトを例外として通知していた。  
JKCommentCrawler はニコ生と NX-Jikkyo の取得が両方完了してからその日のファイルを書くため、先に取得できていたニコ生のコメントも、その試行では保存に至らない。

この失敗が繰り返されると、ファイルは最後に成功した時点の内容で止まり、その後の時間帯が欠ける。  
修正前は、一般の通信エラーでチャンネルをスキップした後も終了コード0になり、末尾には全チャンネルの処理完了を示す文言が出ていた。  
例外は標準出力へ出ていたため、標準エラーのログが空でも収集に失敗している場合があった。

## HTTP/2 の停止原因

HTTP/2 では、受信側が一度に受け取れる量を送信側へ通知する。  
この受信枠を更新する SETTINGS と、設定を受け取ったことを知らせる ACK が、今回の停止に関係している。  
新しい curl-impersonate の既定の接続では、最初に 6MiB を通知し、その直後に 1MiB へ変更する SETTINGS を送っていた。

本番の Caddy 2.10.2 は Go 1.25.0 と golang.org/x/net v0.42.0 を使用していた。  
再現用の Caddy 2.11.4 は Go 1.26.3 と golang.org/x/net v0.55.0 で、こちらでも再現した。  
失敗時は2回の SETTINGS に対して ACK が1回しか返らず、成功時は2回返った。

ACK が1回だけだと、nghttp2 は先に送った 6MiB の設定だけが確認済みと判断する。  
一方、Caddy は後から届いた 1MiB の設定も適用して送信している。  
サーバーは 1MiB を送り切ると受信枠の追加を待ち、クライアントは大きい受信枠の途中だと判断して追加を通知せず、双方の待機が続く。

Go の HTTP/2 サーバーは、未送信の ACK の有無を真偽値 `needToSendSettingsAck` で保持している。  
送信処理が追いつく前に複数の SETTINGS を処理すると、確認すべき回数が1回にまとまってしまう。  
該当箇所には個別の ACK が必要という TODO も残っており、RFC 9113 の設定確認規則と一致しない。[本番で使用される版の実装](https://github.com/golang/net/blob/v0.42.0/http2/server.go)、[RFC 9113 §6.5.3](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.5.3)

したがって、直接のプロトコル違反は Go 側の ACK 欠落であり、curl-impersonate の接続時の振る舞いの変更がそれを顕在化させたと判断する。  
Caddy 以外でも同じ Go 実装と通知順序がそろえば影響しうる。  
通常の応答を返す hyper-h2 サーバーでは完走しており、影響範囲は HTTP/2 の実装と設定の通知順序によって異なる。

## curl の更新で変わった処理

引き金になった処理は、curl のコミット `24b36fdd1585` で追加された。  
転送速度制限の再設計に伴い、`h2_submit()` がリクエスト開始時に受信枠を再計算し、接続時の設定値と違えば `cf_h2_update_settings()` で新しい SETTINGS を送る構成になった。  
旧版が使う curl 8.15.0 には、この再通知処理がない。[該当する curl の変更](https://github.com/curl/curl/commit/24b36fdd1585ea22e5e1f00791f1c20423433cde)

curl-impersonate は [PR #276](https://github.com/lexiforest/curl-impersonate/pull/276) で curl 8.21.0 を取り込んだ。  
そこで新しい再通知処理と、以前からあるブラウザー向けの設定変更が組み合わさった。  
curl-cffi 0.16.0 はこの変更を含む curl-impersonate 2.0.0 を、0.16.3 は 2.2.2 を使用する。

curl-impersonate 2.2.2 の `lib/http2.c` に適用されるパッチでは、次の3点が食い違いを作っている。

1. `populate_settings()` は未指定時にも Chrome 用の設定文字列を使い、`INITIAL_WINDOW_SIZE` に 6MiB を通知すること
2. `cf_h2_initial_win_size()` が参照する `H2_STREAM_WINDOW_SIZE_INITIAL` は 1MiB であること
3. `h2_submit()` は両者の不一致を検知し、1MiB への変更を通知すること。ただし `HTTP2_SETTINGS` を明示した接続では、この処理を通らないこと

今回の停止を引き起こした変更は、組み込まれた C ライブラリが送る HTTP/2 の設定通知にある。  
通常の curl は最初の通知と再計算で同じ関数を使うため、速度制限を指定していない今回の条件では、この食い違いを作らない。  
Chrome 偽装や `HTTP2_SETTINGS` の明示指定で成功する理由も、同じ分岐から説明できる。[curl-impersonate 2.2.2 のパッチ](https://github.com/lexiforest/curl-impersonate/blob/v2.2.2/patches/curl.patch)

## 上流の Issue と修正状況

2026年9月12日時点で、Go, Caddy, curl-cffi, curl-impersonate の公開 Issue・PR を、SETTINGS, ACK, タイムアウト、受信量、バージョンから検索した。  
今回の「接続直後の SETTINGS 2回に対して ACK が1回になり、受信枠の縮小がクライアントへ反映されず停止する」という現象を直接追跡する Issue・修正 PR は、検索した範囲では特定できなかった。  
これは未報告であることの証明ではない。

Go 側の TODO は、2019年8月13日のコミット `74dc4d7220e7` で追加されていた。  
複数の SETTINGS を ACK 前に受け取っても各フレームを個別に確認すべきだと注記しつつ、真偽値で保持する実装は継続している。  
このコミットが修正した [Go #33606](https://github.com/golang/go/issues/33606) は、制御フレームの大量蓄積によるメモリ枯渇への対策だった。[TODO を追加した変更](https://github.com/golang/net/commit/74dc4d7220e7acc4e100824340f3e66577424772)

差分では、ACK を真偽値で保持する既存の処理を変えず、その直前に TODO の2行を追加している。  
ACK の省略は、この攻撃対策が入る前から存在していた。  
コミットのレビュー先は Google 社内の `go-private` で、同じ Change-Id の公開 Gerrit レビューは検索で見つからなかった。

公開されている [Go #33606 のコメント](https://github.com/golang/go/issues/33606#issuecomment-520974109)、[標準ライブラリへの取り込みレビュー](https://go-review.googlesource.com/c/go/+/190137)、[Go 1.13 への取り込みレビュー](https://go-review.googlesource.com/c/go/+/191618)、[当日のリリース告知](https://groups.google.com/g/golang-announce/c/65QixT3tcmg/m/DrFiG6vvCwAJ)も確認した。  
議論は脆弱性修正の再生成手順と各リリースへの取り込みが中心であり、ACK を省略しても通常のブラウザーでは問題ないという判断や、TODO を未対応とする理由は記載されていなかった。  
当時の資料から確定できるのは、仕様上の不足を注記したまま別の脆弱性対策を取り込んだことまでである。

調査時の golang/net の先頭コミット `53e34cd8c561` にも、Go 1.26 以下で使う旧実装に、真偽値で未送信 ACK を保持する処理と TODO が残っていた。  
本番の v0.42.0 と手元の v0.55.0 にも同じ処理があり、Caddy 2.11.4 でも実際に ACK 欠落と停止を確認している。  
長く修正されていない理由について、メンテナの説明は確認できておらず、利用者が少ないためなどと推測で断定できない。[調査時の実装](https://github.com/golang/net/blob/53e34cd8c56120ce92ef5ee7c4cd8510f57f6e8b/http2/server.go#L1627-L1630)

調査時の安定版である Go 1.27.1 と golang.org/x/net v0.59.0 でも、同じ再現プログラムをビルドして3回とも 1MiB で停止した。  
x/net v0.59.0 は Go 1.27 で標準ライブラリを呼ぶ構成になっているため、ビルド時に `server_wrap.go` が選択され、Go 本体の `net/http/internal/http2/server.go` が使われることも確認した。  
最新版の組み合わせにも、この停止を解消する修正は入っていない。[Go のリリース履歴](https://go.dev/doc/devel/release)、[x/net の切り替え処理](https://github.com/golang/net/blob/v0.59.0/http2/server_wrap.go)、[Go 1.27.1 の ACK 保持](https://github.com/golang/go/blob/go1.27.1/src/net/http/internal/http2/server.go#L1617-L1620)

保守対象の Go 1.26.8 と、調査時点の Go 開発版 `a907bb94d08a` にも、同じ真偽値による保持と TODO が残っていた。  
この2版はソース確認のみで、最新版の実行検証は Go 1.27.1 に対して行った。[Go 1.26.8](https://github.com/golang/go/blob/go1.26.8/src/net/http/h2_bundle.go#L5763-L5766)、[Go 開発版](https://github.com/golang/go/blob/a907bb94d08a7ba5292a40b7b8f4ff8fa14499d7/src/net/http/internal/http2/server.go#L1636-L1639)

curl-cffi 0.16.0 のタイムアウト報告として [#837](https://github.com/lexiforest/curl_cffi/issues/837) も見つかったが、こちらは終了処理中のソケットが残る別の不具合である。  
同じバージョンとエラー番号であっても、今回の ACK 欠落が修正済みだという根拠にはならない。

## 比較検証

成功条件は、HTTP 200 に加え、応答の終端まで受信し、データ量と内容が一致することとした。  
本番では同じ終了済みスレッド `/api/v1/threads/26305` を使い、再現用サーバーでは `0123456789abcdef` を繰り返した 4MiB の固定データを使用した。

それぞれの応答の SHA-256 は次のとおりである。

```text
NX-Jikkyo: 17ba1264f4f4b0da62e20f9a341c999eeffc4160e3941b0d5c2b113d7d1d6da5
固定データ: 3cab7815c40973b8fb036c7a2a69b3649882622a4a0a2f1a980efa4ef8545577
```

| 比較対象 | NX-Jikkyo 本番 | 遅延を加えた手元の Caddy |
| --- | --- | --- |
| curl-cffi 0.15.0, HTTP/2 | 全文一致 | 全文一致 |
| curl-cffi 0.16.3, 既定設定の HTTP/2 | 1MiB で停止する試行あり | 1MiB で停止する試行あり |
| curl-cffi 0.16.3, HTTP/1.1 | 全文一致 | この条件は未実施 |
| curl-cffi 0.16.3, 受信枠を明示した HTTP/2 | 全文一致 | 全文一致 |
| curl-cffi 0.16.3, Chrome 偽装の HTTP/2 | 全文一致 | 全文一致 |
| curl-impersonate 2.2.2 の実行ファイル、HTTP/2 | 1MiB で停止 | 成功3回の後、1MiB で停止する試行を確認 |
| 公式ソースからビルドした curl 8.21.0, HTTP/2 | 全文一致 | 全文一致 |
| HTTPX 0.28.1, HTTP/2 | 全文一致 | 全文一致 |
| aiohttp 3.14.3, HTTP/1.1 | 全文一致 | 全文一致 |

Python を介さない curl-impersonate でも止まるため、Python のコールバックや asyncio 固有の問題は原因から外れる。  
通常の curl 8.21.0 は nghttp2 1.63.0 を組み合わせてビルドし、本番と手元の両方で全文一致を確認した。  
ただし TLS などの依存関係は curl-impersonate と完全に同じではなく、この比較単独で全差分を特定したと扱うべきではない。

手元の Caddy へ直接接続すると成功し、TCP 中継で各方向の転送に25ミリ秒の待機を入れると停止を再現できた。  
同じ条件で応答サイズが `1MiB - 1B` と `1MiB` の場合は成功し、`1MiB + 1B` の場合は最後の `1B` を受け取れずにタイムアウトした。  
25ミリ秒は再現に使った設定値であり、発生に必要な最小遅延ではない。

確認応答だけを変える比較では、正常な hyper-h2 サーバーは 4MiB を返せたが、2回目の SETTINGS ACK だけを省くと 1MiB で停止した。  
このサーバーに対して curl-cffi 0.16.0 でも停止を確認したため、0.16.3 だけに限られた問題ではない。  
受信枠を 1MiB または 6MiB に明示する指定と Chrome 偽装は、どちらも SETTINGS を余分に変更する条件を外し、同じ応答を最後まで受信できた。

### Go の ACK 保持だけを変えた比較

TLS の差と Caddy 固有の処理を除外するため、Go 1.26.3 と golang.org/x/net v0.55.0 の `http2.Server.ServeConn()` で、暗号化しない HTTP/2 サーバーを作成した。  
クライアントは curl-impersonate 2.2.2 の同じ実行ファイルを使い、`--http2-prior-knowledge` で接続した。  
サーバーの最初の書き込みだけを50ミリ秒遅らせ、ACK が送信待ちの間に後続の SETTINGS が届く条件を両方へ与えた。

比較用の Go 実装では、`needToSendSettingsAck` の型、送信待ちの判定、送信時の減算、受信時の加算の4箇所だけを変えた。  
サーバーとクライアントの他の処理、コンパイラー、応答内容、遅延条件は共通である。

| Go 側の ACK 保持 | SETTINGS 2回に対する ACK | 3回の取得結果 |
| --- | --- | --- |
| 元の真偽値 | 毎回1回 | すべて 1MiB で停止し、3秒でタイムアウト |
| 未送信の回数を整数で保持 | 毎回2回 | すべて 4MiB を受信し、SHA-256 も一致 |

この比較では TLS 処理自体が存在せず、Go 側の ACK 保持だけを変えると停止が解消した。  
したがって、今回の直接原因を TLS ライブラリの相性とする説明は成立せず、Go の HTTP/2 実装で確認応答が欠けることが原因と判断できる。  
これは原因を分離する実験用の変更であり、本番向けの修正には既存の制御フレーム数制限との整合も必要になる。

### 他クライアントとの通知内容の違い

同じ hyper-h2 サーバーで、各クライアントが送る設定通知と受信枠の追加を記録した。  
正常な確認応答では全対象が 4MiB を全文受信し、SHA-256 も一致した。  
2回目の SETTINGS ACK を省くサーバーでも比較し、既定設定の curl-cffi 0.16.3 だけが 1MiB で停止した。

| クライアント | 接続直後の SETTINGS に含まれる受信枠 | 今回の停止条件との関係 |
| --- | --- | --- |
| curl-cffi 0.15.0 | 6MiB 、通知は1回 | 直後の縮小通知がない |
| curl-cffi 0.16.3, 既定設定 | 6MiB 、続けて 1MiB | 2回目の ACK が欠けると停止 |
| curl-cffi 0.16.3, Chrome 偽装 | 6MiB 、通知は1回 | 明示された設定を保つ分岐を通る |
| curl-cffi 0.16.3, 受信枠の明示指定 | 6MiB 、通知は1回 | 同上 |
| 通常の curl 8.21.0 | 64KiB 、通知は1回 | 以後は WINDOW_UPDATE で受信枠を追加 |
| HTTPX 0.28.1 | 65,535B 、通知は1回 | ストリームへ WINDOW_UPDATE で 16MiB を追加 |

WINDOW_UPDATE は受信を続けるために枠を追加する別種の通知であり、SETTINGS の確認応答待ちとは仕組みが異なる。  
今回成功した他クライアントは、SETTINGS を接続直後に2回送り、受信枠を大きく縮める条件を作っていなかった。  
2回目の SETTINGS 自体がないクライアントでは、省く対象の ACK も発生しないため、この比較を「ACK 欠落への耐性が高い」と読み替えるべきではない。

### Caddy の送受信ログ

Caddy の失敗試行では、送受信の詳細ログに次の順序が記録された。  
設定を2回受け取った後、サーバーが ACK を1回しか送っていないことが判別できる。

```text
read SETTINGS ... INITIAL_WINDOW_SIZE=6291456
read WINDOW_UPDATE ... incr=15663105
read SETTINGS ... INITIAL_WINDOW_SIZE=1048576
read HEADERS ... stream=1
wrote SETTINGS flags=ACK len=0
wrote WINDOW_UPDATE ... incr=983041
wrote HEADERS ... stream=1
```

同じ試行のクライアントは、SETTINGS を2回送信して ACK を1回受信した後、4MiB の応答のうち 1MiB を受け取った時点でタイムアウトした。

## 復旧と再発防止

NXClient の2箇所の AsyncSession を HTTP/1.1 に固定した。  
過去コメントを取得するセッションと、対象スレッドを検索するセッションの両方で通信方式をそろえている。  
NX-Jikkyo の用途で HTTP/2 が必須という制約はなく、HTTP/1.1 にすれば今回故障した SETTINGS と ACK の処理自体を通らずに取得できる。

ニコ生側の NDGRClient は Chrome 偽装を使い、HTTP/3 を優先する。  
今回の未指定接続とは条件が異なり、OAuth 認証を使った実際の過去ログ取得も成功しているため、この事故を理由に Cookie 認証へ戻す根拠はない。  
現状の根拠では、NDGRClient 全体の通信ライブラリを変更するより、NX の通信方式を固定する方が変更範囲が小さい。

HTTPX への変更でも比較対象は受信できたが、ライブラリ全体の長期的な安定性まで証明した結果ではない。  
NX の依存関係をニコ生のブラウザー偽装用ライブラリから分ける価値はあるものの、例外処理やタイムアウトなどの追従も必要になる。  
今回の復旧は HTTP/1.1 固定に絞った。

収集失敗を見逃す処理も修正し、チャンネル単位の再試行が尽きた場合は、他のチャンネルを収集した後に終了コード1を返すようにした。  
標準出力と標準エラーの内容を実行ごとのログへまとめ、前日以前のログを圧縮して14日間保持する。  
今回の停止は応答サイズに依存するため、通信ライブラリの更新時には小さい応答だけでなく、大きな過去スレッドと全チャンネルの取得結果を確認する必要がある。

上流への最初の報告先は curl-impersonate を推奨する。  
旧版では取得できた同じ Go サーバーに対し、更新後の既定設定で受信が停止するため、報告の主題は更新に伴う互換性の後退である。  
初回通知の 6MiB と再計算時の 1MiB の食い違い、設定を明示すると成功する比較結果、Python を介さない実行ファイルでの再現を添え、不要な設定変更が発生する既定動作の修正を依頼するのが妥当である。

Go 側にも、未送信の SETTINGS ACK を件数として保持し、受信した設定通知ごとに返す修正が必要である。  
その際は、既存の制御フレーム数の上限へ含め、過剰な通知を送る相手への制限も維持する必要がある。  
Go の仕様違反と curl-impersonate の更新による互換性の後退は、両方が修正対象になりうる。  

上流への報告や修正の公開、本番 Caddy の差し替えは未実施である。  
収集の復旧は HTTP/1.1 固定によって完了しており、上流での修正を待つ必要はない。

## ニコ生側で返らなくなった155件

9月9日の jk5 について、保存済みコメントのうち155件が再取得では返らなかった。  
これらはすべて同じ投稿者のコメントで、保存済みのその投稿者の155件すべてが、受信した生の Protobuf 全30ページから消えていた。  
他の投稿者の保存済み11,436件は生データに残っており、XML 変換で155件を落とした結果ではない。

取得時に投稿者単位のコメントが返らなくなっていることまでは確認できた。  
ただし、削除の理由や、保存時に削除されたのか配信時に除外されたのかは、公開 API の結果だけでは特定できない。

## 再収集時の保存方針

再収集では、既存の日次収集と同じく `--force` で取得結果をそのまま保存する。  
投稿者単位で返らなくなったコメントを旧ファイルから補うと、ニコ生側の除外に追従する保存方針が変わるため、マージは行わない。

反映前に既存ファイルと取得結果を標準の XML パーサーで読み、件数、日付、投稿順序、`thread` と `no` の重複、消失範囲を照合する。  
時間帯全体が欠けるような大きな減少は個別に調べ、投稿者単位の消失と区別する。  
保存処理には一時ファイルからの置き換えを採用し、書き込みに失敗しても既存の過去ログを保持する。
